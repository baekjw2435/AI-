# 저장 상태 구성 점검 (2026-11-06)

**아스트라 지적:**
- `proven_load()`는 공유 캐시에서 불러온 기록의 작업량에 `PROVEN_BASE`(2³⁰)를 더합니다.
- `tt_save()`는 이 가산값까지 포함한 작업량으로 남길 기록을 골랐습니다.
- 그래서 공유 기록이 그 작업이 새로 계산한 미확정 기록을 밀어낼 수 있습니다.

**점검 방법:** 저장 파일의 기록을 하나씩 세었습니다(`tools/tt_composition.py`). 작업량이 2³⁰ 이상이고 증명된 기록이 공유 캐시에서 온 기록입니다.
- 공유 기록은 모두 증명된 기록입니다.
- 작업량이 2³⁰ 이상인데 미확정인 기록은 그 작업 자신의 맨 윗부분입니다(아래 3절).

| e1 (갉 → 갉죽) | 4,000,000 | 4,000,000 (100%) | **0** |

**알 수 있는 것:**
- **e43, e1:** 1라운드에서 남긴 400만 개도 모두 공유 기록이었습니다.
  - 1라운드 저장 파일은 2라운드가 덮어써서 남아 있지 않습니다.
  - 하지만 1라운드 저장표에는 공유 기록이 1,670만 개 있었습니다. 저장 규칙상 이 기록이 자기 기록보다 모두 앞섭니다.
  - 그래서 2라운드는 1라운드의 자기 탐색 기록을 하나도 이어받지 못했습니다. 이 두 국면에서는 '이어 쓰기'를 제대로 시험하지 못한 셈입니다.
- **면:** 저장표가 꽉 찬 상태에서 공유 기록 1,680만 개가 들어왔습니다. 자기 기록이 최대 그만큼 밀려났습니다.
  - 남긴 4,000만 개 중 절반이 공유 기록이었습니다.
- **덧붙임:** '3GB'로 잡은 저장표는 실제로 2GB(6,710만 칸)였습니다. 저장표 칸 수를 2의 거듭제곱으로 내림하기 때문입니다(`tt_capacity`).

**아직 모르는 것:**
- 이것이 증명 수치(pn/dn) 정체의 원인인지는 확인하지 않았습니다.
- pn/dn은 남은 일의 양이나 남은 시간을 뜻하지 않습니다.
- 네 국면은 현재 예산에서 미확정이며, 필요한 시간은 알 수 없습니다.

## 2. 수정 (`solver_v5/solver_v5.cpp`, `tools/solve_common.py`)

1. **저장할 때 공유 캐시 기록은 빼고 고릅니다.**
   - 공유 기록은 캐시 파일에 이미 있습니다.
   - 예전처럼 함께 저장하려면 `--tt-save-loaded 1`을 씁니다.
2. **새 옵션 `--proven-load-max N`:** 공유 캐시에서 작업량이 큰 기록 N개만 불러옵니다.
   - 실행 도구는 N을 저장표 칸의 25%로 정합니다(환경 변수 `PROVEN_LOAD_FRACTION`, 기본 0.25).
   - 이유: 공유 기록은 교체 우선순위가 높아서 탐색 중에 밀려나지 않습니다. 한도가 없으면 1GB 저장표의 59%(1,970만 칸)를 차지했습니다.

## 3. 추가 수정: 자기 기록의 작업량 상한 (재실행 중 발견)

**발견:**
- 고친 방식으로 e43을 2라운드 돌린 뒤, 맨 위 국면(루트)의 누적 작업량이 1,046,087,680이었습니다.
- 2³⁰(1,073,741,824)에 거의 닿았습니다. 한 라운드만 더 돌리면 넘습니다.
- 넘으면 저장할 때 공유 기록으로 잘못 보고 빼 버립니다. 가장 많이 계산한 맨 윗부분이 빠지는 셈입니다.
- 실제로 면의 옛 저장 파일에는 이런 기록이 이미 있었습니다.
  - 면 → 면벚 2개, 면 → 면접착 3개
  - 작업량 11.2억~16.1억, 모두 미확정
  - 위 1절의 표는 이 기록을 자기 기록으로 고쳐 센 값입니다. 처음 보고에서는 공유 기록에 들어가 있었습니다(20,073,921 / 20,073,922).

**수정:** 자기 기록의 작업량은 2³⁰ − 1에서 멈추게 했습니다. 이제 작업량이 2³⁰ 이상이면 언제나 공유 기록입니다.

**확인:**

  - 수정 전 빌드: 맨 윗부분 3개가 빠져 19,927,547개를 저장했습니다.
  - 수정 후 빌드: 3개가 남아 19,927,550개를 저장했습니다.

## 6. 보완 (2026-11-07, 아스트라 검토)

아스트라가 계산 기록을 보존하는 데 남은 빈틈 두 가지를 짚었습니다. 틀린 승패가 검증을 통과한 문제는 아닙니다. 저장 상태와 공유 캐시는 탐색 힌트일 뿐이고, 확정 결과는 늘 증명을 새로 만들어 검증합니다.

### 6-1. 공유 캐시 한도를 실제 저장표 칸 수로

**문제:**
- 실행 도구가 요청한 메모리(예: 3072MB)로 칸 수를 계산했습니다.
- 실제 저장표는 2GB(67,108,864칸)입니다.
- 그래서 '25%'가 실제로는 37.5%(25,165,824칸)였습니다.

**수정:**
- 계산기에 `--proven-load-fraction`을 더했습니다. 계산기가 실제 칸 수(`tt_capacity`)에 비율을 곱합니다.
- 실행 도구는 비율(0.25)만 넘깁니다.
- 공유 캐시 파일을 합칠 때의 한도(`PROVEN_MAX`)도 실제 칸 수의 절반으로 바꿨습니다.

**확인:**
- 3072MB에서 불러온 공유 기록이 16,777,216개였습니다. 실제 칸의 25%입니다.
- 예전 계산으로는 한도가 25,165,824개라서 캐시 전체 18,601,896개(실제 칸의 27.7%)가 다 들어왔습니다.
- 실행 도구의 칸 수 계산(`table_slots`)이 256MB~4096MB 8가지에서 계산기의 실제 칸 수와 같았습니다.

### 6-2. 옛 고작업량 기록은 불러올 때 바로 교정

**문제:**
- 3절의 상한은 다시 계산한 기록에만 적용됐습니다.
- 다시 펼치지 않은 옛 기록은 계속 공유 기록으로 잘못 분류되어 저장에서 빠질 수 있었습니다.

**수정:** 상태 파일을 불러올 때, 작업량이 2³⁰ 이상인 기록을 이렇게 나눕니다.
- **미확정 기록:** 공유 기록은 모두 증명된 기록입니다. 그러니 미확정 기록은 자기 기록입니다. 작업량을 2³⁰ − 1로 낮춰 보존합니다.
- **증명된 기록:** 작업량만으로는 출처를 알 수 없습니다. 불러오는 공유 캐시 파일과 열쇠(k0, k1)를 대조합니다.
  - 캐시에 있으면 캐시 기록입니다. 상태 파일에서는 넣지 않고 캐시 불러오기에 맡깁니다.
  - 캐시에 없으면 보수적으로 자기 기록으로 보존합니다. 작업량은 가산값을 뺀 원래 값으로 둡니다.
  - 공유 캐시 없이 불러올 때는 대조할 수 없으므로 모두 자기 기록으로 보존합니다.

**확인: 면 → 면접착 옛 저장 파일 (4,000만 개)**

| 분류 | 개수 |
|---|---:|
| 미확정, 작업량 2³⁰ 이상 → 상한 적용해 보존 | 3 |
| 증명, 공유 캐시에 있음 → 캐시에 맡김 | 16,604,333 |
| 증명, 공유 캐시에 없음 → 자기 기록으로 보존 | 3,469,586 |

- 이어 풀고 다시 저장한 파일은 23,298,440개였고, 모두 자기 기록이었습니다. 작업량 2³⁰ 이상인 기록은 0개였습니다.
- Python 점검 도구(`tools/tt_composition.py --cache`)로 따로 세어도 같은 수였습니다.
- 원래 자기 증명 기록 90,717개는 모두 공유 캐시에도 있었습니다. 집중 실험 때 합쳐진 것입니다. 불러오면 캐시 쪽 기록이 대신하므로 잃는 기록은 아닙니다.
- 칸 경쟁과 새 탐색 기록 때문에 조금 줄었습니다.
  - 미확정 기록: 19,835,364 → 19,829,914 (−5,450, 0.03%)
  - 보존한 증명 기록: 3,469,586 → 3,468,526 (−1,060)
- 탐색은 그대로입니다.
  - 새 형식 저장 파일(e43 재실행)에서 이어 풀었을 때, 국면 수·pn/dn·저장표 수치가 수정 전과 같았습니다(30만 국면). 이 파일에는 교정할 기록이 없었습니다.
  - 저장 파일 없이 면 → 면접착을 300만 국면까지 풀어도 같았습니다.
- 옛 파일을 불러오는 시간은 늘었습니다. 면 → 면접착 4,000만 개에 43초가 걸렸습니다. 새 형식 파일에는 이런 기록이 없어서 늘지 않습니다.
