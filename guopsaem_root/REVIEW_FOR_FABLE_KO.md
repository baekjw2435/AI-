## 1. 게임과 규칙

- 끝말잇기를 정해진 단어 목록 안에서만 합니다.
  - 받은 음절 X로 시작하는 단어를 내야 합니다. 두음법칙으로 바꾼 꼴 conv(X)로 시작해도 됩니다.
  - 한 경기 안에서 같은 단어는 다시 쓸 수 없습니다.
  - 낼 단어가 없으면 집니다.
- **표준두음법칙(엔진 표)**
  - 받침과 관계없이 다음 세 가지만 바뀝니다.
    - ㄹ + ㅑㅕㅖㅛㅠㅣ → ㅇ
    - ㄹ + ㅏㅐㅗㅚㅜㅡ → ㄴ
    - ㄴ + ㅕㅛㅠㅣ → ㅇ
  - **한쪽 방향, 한 단계**입니다. 락을 받으면 락·낙 단어를 다 쓰지만, 낙을 받으면 낙 단어만 씁니다. 려 → 여는 되지만 려 → 녀 → 여처럼 이어 바꾸지 않습니다.
  - 구현: `guopsaem_root/verifier_v3/verify_v3.py`의 `conv()`
- **첫 제시 기준:** 그 음절을 목록 밖의 단어로 넘겨받아, 목록 단어가 하나도 쓰이지 않은 국면입니다. 받은 사람이 먼저 둡니다.
- 사전 두 개

    - 94음절 확정: 받으면 승 64, 받으면 패 30. 정리는 `basic_root/SOLVED_KO.md`

## 2. 신뢰의 사슬 (판정이 맞으려면 무엇이 맞아야 하나)

- **판정 원칙:** 계산기가 쓴 증명서를 독립 검증기가 통과시킨 것만 확정합니다. 계산기 자체는 믿지 않습니다.
- 그래서 맞아야 하는 것은 아래 다섯 가지입니다.
  1. 규칙 구현: `conv()`, 사전 읽기, 국면(첫 음절 + 둔 단어들) 해석
  2. 모델과 정규형의 값 보존: `ModelV3.normalize` (`verifier_v3/verify_v3.py`)
  3. 증명 형식과 검증기의 완전성 검사: `verifier_v4/FORMAT.md`, `verify_v4.cpp`, `verify_v4.py`
  4. 수락 조건: 종료 코드 0, `verified: true`, 기대 결과, `state_storage == "deflate-exact"`, 사전·국면·입력·증명 SHA-256 일치 (`guopsaem_root/tools/solve_common.py`의 `verify`)
  5. 첫 수별 증명을 합칠 때의 규칙: `verifier_v4/merge_root_v4.py` (합친 파일 전체를 다시 검증합니다)
- **우리의 전제:** 계산기 버그는 틀린 판정을 만들 수 없고, 검증 거부·증명 실패·시간 낭비로만 나타납니다. 이 전제가 맞는지도 봐 주세요.
  - 예: 저장표 해시 충돌, 여러 스레드 경쟁, 저장 상태와 공유 캐시는 탐색 힌트일 뿐입니다.

## 4. 검토 질문 (중요한 순서)

1. **정규형의 값 보존** (`ModelV3.reduce`, `static_labels`, `normalize`)
   - 왕복 쌍 지우기와 고리 짝수 지우기를 출발이 하나인 묶음끼리만 하는 것이 맞는가. 공유 묶음(한 단어를 여러 꼭짓점에서 씀)을 빼는 이유는 README_KO.md에 있습니다.
   - 고정 라벨은 최소 고정점으로 정합니다. L 후속이 있으면 공유 고리가 있어도 W입니다. 모든 비고리 후속이 W일 때 쓰는 고리 규칙만, 공유 고리가 남은 꼭짓점에는 적용하지 않고 라벨 없이 둡니다. 이 규칙과, 고리 짝수 지우기(1단계)와 고리 규칙(3단계)이 서로 기대는 부분이 맞는가.
   - 핵심만 남기기에서, 라벨 붙은 꼭짓점으로 가는 묶음을 지우는 것이 맞는가. 우리 논증은 "라벨 없는 꼭짓점의 후속에는 L이 없으므로 그 수는 모두 지는 수"입니다.
2. **v4 검증기의 완전성**
   - L 마디는 정규 국면에서 낼 수 있는 모든 묶음을 한 번씩 적어야 하고, W 마디는 L 자식 하나를 적습니다. 고정 라벨 리프와 같은 마디에 다시 도착할 때의 비교(바이트 단위)를 봐 주세요.
   - 루트에서 닿지 않는 마디, 머리글과 모델 불일치, 합친 증명도 봐 주세요.
   - C++와 Python 두 검증기가 같은 것을 같은 기준으로 받는지도 봐 주세요.
3. **817 결과와 현재 모델의 관계**
   - 817 결과는 원본 `verify_v2.py`(합쳐진 두음 모델)로 확인했습니다.
   - 지금 817 다른 첫 수 연구는 v4 증명과 C++ 검증기로 확인합니다.
   - 두 모델이 817에서 같은 게임이라는 확인(`basic_root/alt_first_moves/build_targets.py`의 `model_check`)이 충분한가.
4. **계산기**
   - 증분 정규화(`gen_child`, `apply_child`)가 기준 정규화(`ref_canon`)와 같은가. `--selfcheck`로 대조하고 있습니다.
   - 증명 생성(`Emitter`)이 검증기와 같은 정규형을 쓰는가.
   - 저장·재개와 공유 캐시 코드(`tt_save`, `tt_load`, `proven_load`, `mark_in_cache`, `PCSelect`)가 계산 기록을 잃지 않는가. 이 부분은 최근 세 번 고쳤습니다(아래 7절).
5. **연구 방향**
   - 아래 6절의 측정을 볼 때 우리 결론이 맞는가.
   - 정확성을 유지하면서 큰 국면의 탐색을 줄일 방법으로 무엇이 가장 유망한가.

- 원본 v2 검증기의 두음 표는 엔진 표와 다릅니다(럼·렌·렉·렛·뤄 등). 817에는 차이 나는 음절이 없습니다.

  1. 공유 캐시 기록이 저장 상태를 채우던 문제
  2. 작업량이 2³⁰을 넘은 자기 기록을 공유 기록으로 오인하던 문제
  3. 캐시 한도를 요청 메모리가 아니라 실제 칸 수로 계산하고, 옛 기록은 실제로 불러올 공유 기록과 대조하도록 바꾼 것
