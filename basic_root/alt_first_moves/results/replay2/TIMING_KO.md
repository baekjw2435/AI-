# 증명서 쓰기와 검증 시간: 측정과 개선 (2026-11-12)

재생으로 탐색이 몇 초가 되자, 남은 시간은 거의 증명서 쓰기와 검증이었습니다(준결승: 전체 169초 중 탐색 4초, 쓰기 45초, 검증 117초). 그래서 두 구간이 시간을 어디에 쓰는지 재고, 가장 큰 부분을 하나씩 고쳤습니다.

## 결론

- **검증:** 시간의 60%가 '도착한 국면을 압축해 담아 두기'였습니다. 압축기 설정 두 값을 바꿔 검증이 약 2배 빨라졌습니다(국면당 55 → 26마이크로초). **검사는 그대로입니다.**
- **증명서 쓰기:** 시간의 76%가 '자식마다 기준 정규화를 다시 하기'였습니다. 이를 건너뛰는 선택 옵션(`--emit-check 0`)으로 쓰기가 약 3배 빨라졌습니다(국면당 20 → 6마이크로초). 탐색 경로가 같으면 증명서 파일도 바이트까지 같습니다.
- **비교용 12개의 재생 합계는 1,513초에서 1,016초가 됐습니다.** 탐색이 대부분인 풍력을 빼면 974초에서 497초입니다(약 절반).
- 판정은 하나도 바뀌지 않았습니다. 12개 모두 다시 확정됐습니다.

## 1. 검증기 (`guopsaem_root/verifier_v4/`)

**측정.** `verify_v4.cpp`에 시간 측정만 끼운 사본(`profile/verify_v4_timed.cpp`)으로 쟀습니다. 교역의 증명서(888,639국면, 52.3초)입니다.

| 부분 | 시간(초) | 비율 |
|---|---:|---:|
| 도착한 국면을 압축해 기록 | 31.5 | 60% |
| 자식 국면 정규화 | 7.7 | 15% |
| 펼칠 때 정규형 확인 | 8.0 | 15% |
| 기록한 국면 꺼내기 | 3.7 | 7% |
| 증명서 읽기(gzip, JSON, sha256) | 0.4 | 1% |

**압축 설정 비교.** 권력의 증명서(202,373국면)에서 설정만 바꿔 잰 값입니다.

| 설정(수준 / memLevel / 방식) | 검증 전체(초) | 국면 기록(마이크로초) | 담는 크기(바이트/국면) |
|---|---:|---:|---:|
| 6 / 9 / 기본 (바꾸기 전) | 12.6 | 37.1 | 129.8 |
| 1 / 8 / 기본 | 6.4 | 10.4 | 170.8 |
| 6 / 8 / 허프만만 | 6.1 | 7.8 | 136.8 |
| 6 / 9 / 런 길이(RLE) | 7.1 | 11.3 | 126.3 |
| **6 / 4 / 런 길이(RLE) (채택)** | 5.9 | 8.1 | 126.3 |

- 국면은 대부분 0인 바이트열이라, 런 길이 방식이 가장 빠르면서 크기도 가장 작았습니다.

**변경.** `verify_v4.cpp`의 압축기 설정 두 값(방식, memLevel)만 바꿨습니다.
- 바뀐 것은 검증기가 스스로 계산한 국면을 메모리에 담아 두는 방법뿐입니다. 담아 둔 국면은 전과 같이 풀어서 모든 바이트를 비교합니다.
- 증명서 형식, 검사 항목, 수락 조건, 출력은 그대로입니다. `state_storage`도 `deflate-exact` 그대로입니다.

**확인.** 바꾸기 전 빌드와 바꾼 빌드에 같은 파일을 주고 종료 코드와 출력(오류 문구 포함)을 비교했습니다(`tests/diff_old_new.py`).

| 시험 | 규모 | 다른 결과 |
|---|---|---:|
| 무작위 사전의 증명서와 망가뜨린 증명서 | 12,654회(둘 다 수락 4,522, 둘 다 거부 8,132) | 0 |
| 보관한 실제 증명서(실험 1·2 보관본, 원본 증명서) | 46개, 86회 | 0 |
| 겨냥한 공격 | 118건 | 0 |
| 망가뜨린 증명서 40종, 정상 변형 9종 | 승급 증명서 | 전과 같음 |

자세한 것은 `guopsaem_root/verifier_v4/README_KO.md`의 마지막 절에 있습니다.

## 2. 증명서 쓰기 (`solver_v5_replay`)

**측정.** 계산기에 구간별 시간(`emit_profile`)을 넣어 쟀습니다. 교역(888,639국면, 17.9초)입니다.

| 부분 | 시간(초) | 비율 |
|---|---:|---:|
| 자식마다 기준 정규화 다시 하기 | 9.4 | 52% |
| 그 결과로 국면 다시 만들고 대조 | 4.3 | 24% |
| 자식 만들기(증분) | 1.5 | 8% |
| gzip으로 쓰기 | 0.9 | 5% |
| 이미 쓴 국면 찾기 | 0.6 | 4% |
| 그 밖 | 1.2 | 7% |

- 계산기는 증명서를 쓸 때 자식 국면마다 '기준 정규화'로 다시 계산해 탐색 때 쓰는 '증분 정규화'와 대조합니다. 계산기 스스로 하는 점검입니다. 검증기는 어차피 모든 국면을 처음부터 다시 계산합니다.

**변경.** 선택 옵션 `--emit-check 0`을 더했습니다. 기본값은 전과 같은 1입니다.
- 0이면 고정 라벨이 아닌 자식은 증분 정규화만으로 만듭니다. 고정 라벨인 자식은 전처럼 기준 정규화를 거칩니다.
- 탐색 경로가 같고 두 정규화가 같으면 증명서는 같은 파일입니다. 탐색이 길어 저장 시점에 따라 경로가 달라지면 파일도 달라질 수 있습니다(아래 풍력). 정규화가 다르다면 검증기가 거부하는 증명서가 나올 뿐입니다.
- **독립 검증은 그대로 필수입니다.** 이 옵션으로 쓴 증명서도 검증기를 통과해야 확정하고, 통과하지 못하면 미확정입니다.

**확인.**
- 무작위 사전 4,270번 재생에서 `--emit-check 0`의 증명서가 모두 기본 방식과 같은 파일이었습니다.
- 아래 12개 중 11개의 증명서가 고치기 전과 같은 파일입니다. 풍력만 다릅니다(아래 설명).

## 4. 남은 것

| 후보 | 예상 효과 | 하지 않은 이유 |
|---|---|---|
| 검증기: 정규화 두 번(지금 검증 시간의 53%)을 빠르게 | 정규화가 2배 빨라지면 검증 약 1.4배 | 모델 코드를 고치는 일이라 검토가 먼저 필요 |
| 검증기: 방금 기록한 국면을 바로 꺼낼 때 압축 풀기 생략 | 검증 최대 약 15% | 검증기의 흐름이 바뀜 |
| 계산기: 기본 계산기(`solver_v5`)에도 `--emit-check` 넣기 | 직접 탐색의 증명서 쓰기 약 3배 | 실험용 사본에서 먼저 확인하려고 |
| 같은 증명서가 여러 국면에서 통과할 때 쓰기 생략 | 사례에 따라 쓰기 시간 전부 | 미리 알 수 없어 검증을 한 번 더 해 봐야 함 |
| 증명서 크기 줄이기(국면 수 줄이기) | 쓰기와 검증 모두 | 방법을 아직 재지 않음 |

- 고친 뒤 승을 넘겨주는 첫 수는 전체 약 66~73초 중 검증이 48~52초입니다. 다음으로 줄일 곳은 여전히 검증입니다.
