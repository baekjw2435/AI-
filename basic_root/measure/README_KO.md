# 반복 탐색 측정 (2026-10-29)

아스트라의 제안에 따라, 탐색 시간이 어디에 쓰이는지 나눠서 쟀다. 판정을 위한 계산이 아니라 측정용이다. 승패 기록은 `RESULTS_GYEOK.md`에 있다.

## 측정 방법

`solver_v3m.cpp`는 `solver_v3.cpp`에 표본 측정기만 붙인 사본이다. 탐색 방식은 바꾸지 않았다. 1스레드에서 원본과 탐색 횟수가 똑같이 나온다.

- `--sample-bits B`: 국면 지문(h0)의 B비트가 0인 국면만 정확히 추적한다. 같은 국면은 언제나 표본 안이거나 언제나 밖이다.
- 표본 국면을 펼칠 때마다(탐색 함수 호출 한 번) 다음 다섯 가지 중 하나로 센다.

| 분류 | 뜻 |
|---|---|
| new | 처음 펼침 |
| present | 전에 펼쳤고 저장표 칸이 남아 있음 (df-pn의 일반적인 재진입) |
| lost_open | 전에 펼쳤고 칸이 지워졌으며, 마지막 값은 미확정 |
| lost_proven | 전에 펼쳤고 칸이 지워졌으며, 마지막 값은 확정 (확정 기록 손실 때문의 재탐색) |
| concurrent | 다른 스레드가 같은 국면을 펼치는 중 |

- 칸이 지워진 국면 중 나중에 다시 필요해진 비율도 따로 센다.
- 본 탐색과 증명 출력 단계는 나눠서 센다.
- `--sample-dump PATH`: 표본 국면 목록을 저장한다. `overlap.py`로 실행 사이의 공유율을 계산한다.

## 1. 가장 어려운 격찬 국면, 저장표 4GB와 8GB

대상은 [격찬, 찬성표, 표현력, 역습, 습격]이다. 4스레드, 표본 1/1024이다. 4스레드 실행은 매번 조금씩 다르다. 같은 4GB 설정의 원래 계산은 탐색 1,523초였다.

| 항목 | 4GB | 8GB |
|---|---:|---:|
| 본 탐색 | 1,474초 | 1,468초 |
| 증명 출력 | 329초 | 327초 |
| 탐색 횟수 | 25.8억 | 25.1억 |
| 증명 노드 | 7,554,212 | 7,454,921 |
| 최대 메모리 | 4.9GB | 9.0GB |

**본 탐색의 펼침 분류**

| 분류 | 4GB | 8GB |
|---|---:|---:|
| new | 50.7% | 53.7% |
| present | 37.8% | 39.7% |
| lost_open | 9.5% | 5.7% |
| lost_proven | 1.9% | 1.0% |
| concurrent | 0.0% | 0.0% |

**칸이 지워진 국면**

| 항목 | 4GB | 8GB |
|---|---:|---:|
| 한 번 이상 지워진 국면 | 92.7% | 83.2% |
| 그중 다시 필요해진 국면 | 18.5% | 12.6% |
| 확정 기록이 지워진 국면 중 다시 필요해진 것 | 13.8% | 8.2% |

**읽는 법**
- 저장표 교체가 57%였지만, 지워진 칸 때문에 생긴 재탐색은 본 탐색의 11.4%였다. 확정 기록 손실만 따지면 1.9%다.
- 메모리를 두 배로 늘리면 그 재탐색은 6.7%로 줄었다. 그러나 탐색 시간은 같았다(차이 0.4%, 실행 간 차이보다 작음). 표가 커지면 메모리 접근이 느려지는 비용이 줄어든 재탐색을 상쇄한 것으로 보인다.
- 처음 펼친 서로 다른 국면은 약 13억 개로, 증명 노드의 약 175배다. 가장 큰 비용은 증명에 들어가지 않는 국면을 처음 탐색하는 것이다. 그다음이 df-pn의 재진입(38%)이다.

**증명 출력**
- 지워진 국면을 다시 푼 펼침은 약 565만 회로, 본 탐색의 0.2%다.
- 출력 시간 329초의 약 절반은 gzip 압축이다. 압축 전 증명은 11.2GB이고, gzip 6단계로 압축하는 데 162초가 걸렸다. 1단계는 81초지만 파일이 2.9배 커진다.
- 따라서 앞서 아스트라에게 "증명 출력 때 106만 국면을 다시 풀었어(전체 시간의 19%)"라고 쓴 문장은 바로잡는다. 19%는 출력 단계 전체의 비중이다. 다시 풀기는 그중 작은 부분이고, 나머지는 증명 줄을 만들고 압축하는 시간이다.

## 2. 이웃 국면 사이의 공유

1스레드, 300초, 1GB 표, 표본 1/256이다. 각 칸은 열 국면이 펼친 국면 중, 행 국면도 펼친 비율 / 행 국면에서 확정된 비율이다.

| 행 \ 열 | 습격 | 습식 | 역방향 | 찬탄쪽 격식 |
|---|---:|---:|---:|---:|
| 습격 [..표현력,역습,습격] | - | 0.3 / 0.2% | 0.7 / 0.2% | 0.2 / 0.1% |
| 습식 [..표현력,역습,습식] | 0.1 / 0.1% | - | 0.6 / 0.2% | 0.0 / 0.0% |
| 역방향 [..표현력,역방향] | 0.7 / 0.2% | 2.0 / 0.6% | - | 0.1 / 0.1% |
| 찬탄쪽 격식 [..역습,습격,격식] | 0.2 / 0.1% | 0.0 / 0.0% | 0.1 / 0.1% | - |

대조 실험으로 습식 국면을 다른 설정(256MB 표, 2스레드)으로 다시 풀었다. 이때는 67.9~76.8%가 겹쳤다. 측정 방법은 공유를 잡아낸다. 따라서 이웃 국면 사이의 공유가 낮은 것은 실제다.

**읽는 법:** 형제·사촌 국면은 사용한 단어 집합이 달라서, 축약 뒤에도 같은 국면이 거의 생기지 않는다. 여러 국면이 함께 쓰는 확정 국면 저장소는 이 연구 방식에서는 효과가 거의 없을 것이다.

## 3. 같은 국면을 다시 푼 비용 (격 연구 전체)

`progress.log`의 탐색 260회, 실행 시간 합계 100,132초를 분류했다.

| 분류 | 비율 |
|---|---:|
| 결론이 나지 않았고, 나중에 같은 국면을 처음부터 다시 풂 | 27% |
| 결론이 나지 않았고, 다시 풀지 않음 (다른 갈래로 해결됐거나 보류) | 40% |
| 결론이 남 | 33% |

같은 국면을 다시 풀 때는 표본의 68~77%가 겹친다(2절 대조 실험).

## 결론: 재사용 설계의 우선순위

1. **같은 국면의 계산 이어 하기.** 시간 제한으로 멈춘 실행의 저장표를 디스크에 남기고, 더 긴 예산으로 다시 풀 때 불러온다. 이번 연구에서는 최대 27%의 시간이 여기에 해당했다. 아스트라가 제안한 1초 → 10초 → 1분 단계 예산도 이 기능이 있어야 낭비가 없다.
2. **증명 출력 압축을 별도 스레드로.** 증명 줄 만들기와 압축을 동시에 하면 출력 시간을 절반 가까이 줄일 수 있다. 전체 시간으로는 약 9%다. 파일 형식은 그대로다.
3. **여러 국면이 함께 쓰는 확정 국면 저장소는 보류.** 이웃 국면 사이의 공유가 2% 이하였다.
4. **본 탐색의 큰 비용은 수 정렬과 초기값 쪽이다.** 처음 탐색하는 국면이 증명의 약 175배라서, 메모리보다 탐색 순서를 개선해야 큰 효과를 기대할 수 있다.

이 결론은 격찬의 한 갈래와 그 이웃 네 국면에서 나온 것이다. 다른 음절이나 큰 사전에서는 비율이 다를 수 있다.

## 파일

- `solver_v3m.cpp`: 측정용 탐색기. 빌드는 solver_v3와 같다.
- `overlap.py`: 표본 국면 목록 사이의 공유율.
- `calib.py`: 짧은 탐색의 pn/dn 기울기와 최종 결과 비교. `progress.log` 형식을 읽는다.
- `raw/`: 각 실행의 결과 JSON.
